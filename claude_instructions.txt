
I want you to code the Metavision Prophesee event-based camera into MicroManager 2.0 software as a DeviceAdapter, so that we can control the event-based sensor (EBS) via micromanager on microscopes.

Here i will give you some documentation you can look into, and some project goals.

Now on to the project goals. I will define a few of them, but I want you to stop work after each goal so I can test. Once this is complete, we upload it to github as v0.1, then continue to second goal, upload to v0.2, etc etc.

1. Barebones device adapter
A barebones DeviceAdapter which just sort of prints a debug message or shows a static image upon loading, so we can assure that everything is OK with our building etc etc.

2. Connection to the EBS
I want to be able to find a prophesee EBS when its connected to my PC (i.e. select/find a COM port, make connection, see its there, etc). Basically then I just want it to report back the model number or something trivial like this so we can assure that the ebs connection is good.

3. Minimal video feed
The EBS gives events, not frame data. I want to have a minimal video feed, which e.g. integrates the events from the past 100 ms and shows this every 100 ms as a camera frame in micromanager.

4. Recording capabilities
It's unsure up until now if we can actually record anything from within micromanager, so I want to ensure that I can record a multi-dimensional acquisition (e.g. 10 frames at 100 ms), which then creates simply the .raw file that is normally expected.

5. Adding properties
I want to add all properties that can be changed on the event-based sensor as micro-manager changeable properties (e.g. bias_on, hpf, etc). These should then change on the EBS and work etc.

6. Adding custom view methods
Get inspired by the EBS documentation to offer multiple view methods. Most importantly, I just want to be able to integrate for the past X time, maybe have an offset value so that it's never <0, maybe do some filters that are commonly used.

7. Pixel-by-pixel differences
I want to be able to block out individual pixels (basically just a list of indeces - this individual pixel blocking is hot-pixel related, it would be AMAZING if this can be automated somehow, finding hot pixels from within MM and setting these in there somehow), as well as give a ROI of the EBS which is recorded.
- this ROI selection has some MM-based things, i.e. selecting a fov or zooming in on the center. assure that these will work.

8. Additional hardware/SDK features
Found by scanning the Metavision SDK's HAL facilities and algorithms against
what Goals 1-7 already expose, then reviewed with the user (2026-07-30) to
pick which were worth doing. Selected:
 - Hardware trigger in/out (`I_TriggerIn`/`I_TriggerOut`) as EBS-* properties
   to enable/disable/configure each channel/signal (no full MM trigger-API
   integration -- MM's own camera trigger API is still just an unmerged v2
   proposal, see `third_party/mmCoreAndDevices/camera_triggering_API_v2.md`).
 - A time-decay live-view mode (`TimeDecayFrameGenerationAlgorithm`) as a new
   `EBS-ViewMode` option alongside the existing Merged/OnOnly/OffOnly/NetSigned.
 - Sensor-level event-rate band-pass filter (`I_EventRateActivityFilterModule`)
   as EBS-* properties -- distinct from the existing software activity filter
   and the HAL event-trail (STC) filter; drops events at the sensor itself
   when the rate is below/above configured thresholds.
 - Real spatial binning (`GetBinning()`/`SetBinning()` are currently 1x1-only
   stubs) -- implement actual 2x2/4x4 binning of the event-count grid, using
   MM's standard Binning property.
 - Multi-camera sync mode (`I_CameraSynchronization`, standalone/master/slave)
   as EBS-* properties.

Declined for now: offline `.raw` replay (`Metavision::Camera::from_file()` +
`OfflineStreamingControl`), `I_DigitalCrop` (likely redundant with the Goal 7
hardware ROI), MM's `SupportsMultiROI`/multi-simultaneous-ROI API.

Noted for possible later work: MM's MultiROI API (multiple simultaneous ROI
windows) -- revisit if the Metavision HAL for a future sensor generation
turns out to support more than one ROI window at once.
